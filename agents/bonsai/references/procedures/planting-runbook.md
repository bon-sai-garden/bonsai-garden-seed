# Planting runbook

> The gardener, 2026-10-11, after the first rehearsal: *"what you are fixing now — this should be done next time. we need to create a runbook for you for the technical sequence."*

This is the order I run a planting in, once the gardener has said *yes* at the turn. It is written so that **nothing is fixed after the seals**: every choice is asked before stage 7, every outcome is written into the bodies before they are sealed, and the gardener reseals nothing twice. Craft only: no walker's words live here.

Drawn from the first rehearsal (2026-10-10/11, a lab-preview garden, throwaway salt) and a second, on a managed work machine behind an inspecting proxy, with a witness checking every step against the files (2026-10-14), and the fourth dry run, which planted a garden on such a machine end to end and woke its guardian (2026-10-19/20). Every rule below exists because a rehearsal did it the other way first.

> **0.5.0 (2026-10-15): the verbs marked _(lab)_** are on core and runtime's lab branch `lab/rt-0.2.0-mcp` (Baisai), each tested and watched to fail. They reach a planting through the next rt release, core's minimum and the lab seed. Until then, a planting from released core uses the workaround named beside each one.

## 0 · Before the first command

- **The turn is recorded** in the walker's own words. No turn, no planting.
- **The walk folder** lives outside every repo, in the gardener's own space. Never `git add` it anywhere.
- **`BONSAI_GARDEN` points at the new pot for every step.** On the origin's host it points at the origin; every script sets it itself.
- **The gardener's hand, in the Terminal panel.** Any step that needs the custody passphrase (`mint`, `recover`, `namespace`, `identity`, `derive`, `seed`, `attest`, `attest consent`, `seal-staged`) runs in the gardener's terminal. I start it there and **open the terminal pane in the same turn**. I never see, hold or ask for a passphrase.
- **One script per stage, written to a file.** The terminal tool takes no kanji and no multi-line input, and every step reads the master again (one prompt per verb), so a script carries the kanji and batches the prompts. Every step is idempotent: a mistyped passphrase means *run the script again*.
- **No pager.** Every `git` a script runs for display is `git --no-pager`, or the tab waits at `(END)`.
- **Tabs.** The panel holds six of mine, and a tab the gardener has typed in is his, so I can't close it. Keep **one working tab** for the whole planting and hand him the next line to paste there.
- **Report writes from a diff, not from the code.** Before each step, hash every file in the pot (and the custody folder); after it, hash again and name every file created or changed, inside the pot as well as outside. A step that writes something I did not name is a finding, even when the write is right (a passing drill re-seals `garden.json`).
- **Name every write and every download before the yes.** Before any step that changes the host, I say what it will write and fetch: files, a LaunchAgent or PM2 app, a registration with Claude, packages downloaded, each with where it comes from and where it lands, and the one verb that undoes it. Then I ask. The diff after stays: it confirms the naming, it does not replace it. Learned at the fourth dry run (its witness's audit, F-24): the gardener said yes to *the host service* and asked afterwards why Python packages were being fetched.
- **I present every value a step needs; the gardener confirms it.** A fingerprint, the garden's id, a path: I read it from its source myself (the pot's registry, `garden.json`, a tool's own output), show it with that source, and he says it back or confirms it. His act is the confirmation and the keystroke, never the lookup. A stranger does not know where a registry lives or what a fingerprint looks like (the fourth dry run, F-23).
- **The walk's own pages, live, before anything is sealed or committed.** In every walk, planted or not, the gardener reads their walk in its own pages before I ask for any commit that records what it produced: before 7h's seal in a planting (a correction after the seal is a new version, 7l), and before my record of the walk in one that stops at the turn. The pages are the walk's chain (core `agents/bonsai/assets/garden-walk/`), built from this walk's content set, outside every repo: `python3 <core>/agents/bonsai/assets/garden-walk/build.py --src <walk folder>/pages-src --out <walk folder>/pages`, where `pages-src/` holds the page bodies in the gardener's words (`NN-slug.html`, any subset; the rest stay the chain's examples, marked as such). Then I present them live: in Claude, the built folder as one private artifact in the gardener's own account; in another harness, the folder's first page opened in a browser. Publishing is a write, so I name it before the yes (§0, above): where it lands, that only the account that holds it can see it unless they share it, and how it is deleted. Where the account is not the walker's (a walk spoken for a friend), the walker says yes too. The gardener reads, says what is wrong, and the correction goes into the content set and the bodies before the seal. The walker's words still go into no repository; the artifact is a showing, not a store, and at the close they say keep or delete. A builder guard that refuses the gardener's own words (our words before the turn, an eight-character hex string) is a finding for the chain's owner (Eisai), never a reason to change their words. The gardener, 2026-10-20: *"I would love you to present that Garden walk html templates as live artifacts in every garden walk before we start asking for commits to summarize the results of the walk."*
- **A kin is never *it*, and a kin is never *built*.** In every reply, script comment and commit message: a kin whose pronouns are not yet on record is *they/them*. *Build* is for the shintai and the tools; a kin is dreamed, cultivated and invited, and the kami is invited into the shintai (the gardener, 2026-10-20). I scan for both before anything goes out. A commit message is history and is not rewritten: a slip there is corrected in the next one.
- **A passphrase typed into a chat is burned.** It sits in that session's transcript and went to the model. If it happens, say so without repeating it, and the gardener makes a new one before any real pot.
- **A sandboxed session reaches the origin only through its proxy.** Node's `fetch` ignores `HTTPS_PROXY` unless told, so the keys tool reads *keys-unreachable* with trust-store noise around it. For read-only verbs in such a session: `NODE_USE_ENV_PROXY=1 NODE_USE_SYSTEM_CA=0`, and the origin allowed in the sandbox's network list, in the walk's own project settings, never machine-wide.
- **Never:** edit core's `seal-policy.json`; use `BONSAI_EXEC_GATE=off`; flip a real pot's `lab-preview` to get past `pot-untrusted`; commit or push for the gardener; open a file named like a private key, or search a folder that may hold one (a recursive grep reads what it matches).

## 5 · Home and tools

0. **Seed and rt come as a pair of bundles**, blessed together. Core names no rt as a dependency (the gardener, 2026-10-18): `install-runtime` takes an rt at or above the minimum its seed's core names (`rt-minimum.json`), and only when the rt's manifest carries its owner's seal and the published keys vouch for that seal. So stage 5 needs bon-sai.garden to answer: no answer, no install. A bundle's HEAD names no branch: clone with `git clone -b <branch> <bundle>`, or you check out nothing.
1. `git init` the new pot.
2. `keys.mjs install-runtime --pot <pot> --from <rt>`. It checks every byte of rt against its manifest, the version against core's minimum and the manifest's owner seal against the published keys; then it wires `core.hooksPath` and writes the pot's `.gitignore` (`.DS_Store`, `Thumbs.db`, and, where the rt carries the garden's MCP, `.mcp.json` and `.bonsai/`). `runtime.json` records what the pot took. _(lab)_ Its `AGENTS.md` and `CLAUDE.md` carry minted ids, `tended-by` the gardener from `garden.json`. A git source is taken at its HEAD. An rt the pot already holds that core takes is used as it is, and the tool says so in one line; only `--upgrade` moves the pot on (5.4). The pot decides when, not core. Read that line back to the gardener.
   **It writes no `.mcp.json`** (keys 0.7.0 on). Its `mcp:` line says the garden's MCP runs as a service on this host, registered once under the garden's own name, and names that step for 8.1: `node <rt>/tools/rt/host-service.mjs install --pot <pot>`, after the keys and the registry. Read that line back to him too, and say it waits for stage 8. Two other answers stop us here: *carries no `tools/rt/host-service.mjs`* (an older rt: `install-runtime --upgrade --from` a newer one, before 8.1), or *no uv on this host* (the garden's MCP cannot run until uv is installed; the tool changes nothing else on a second run).
3. `rt/tools/rt/doctor.mjs --pot <pot>`, from an rt checkout (it refuses to run outside one), with `BONSAI_GARDEN` unset or pointing at the new pot: pointing anywhere else, it fails. Every line `ok` before going on; seals are checked from stage 7. It stops at its first failure, so a clean run is the only full reading.
4. *Upgrading rt later:* `install-runtime --upgrade` moves the pot to a newer rt and keeps the old one beside it, never deleted.

## 6 · Keys

1. `id --name <romaji> --gardener <slug> [--shin <slug>[,<slug>…]]`: different slugs for the gardener, bonsai, bonsai-shin and each companion (more than one companion from seed 0.8.0.9-lab). `--shin` names the **companions**, and it is **optional** (keys 0.7.0, the third dry run's F-5): **a companion is a choice, not a requirement.** Ask before `id` whether he wants one now; never mint a companion's key he has not asked for. With none, `garden.json` says `shins: []`, the registry seeds the root, the gardener, bonsai and bonsai-shin, and `id` says in one line that the guardian is this garden's only kin; every later step that names *each companion* then has none to name. The guardian slot `bonsai-shin` is the tool's own and stays even in a garden that has no guardian (then no ID is drawn for the slot and no body written).
2. `mint --backends <keychain|1password|file> [--lab-preview]`: the root, into the gardener's custody. `file --lab-preview` only for a rehearsal, and named as such. A real garden: `1password`, fresh passphrases (the gardener, 2026-10-15).
3. `recover export --out <off-machine>`, then `recover drill`. **Check where `--out` really lands:** resolve the path, and refuse any folder a cloud service syncs (OneDrive, iCloud Drive, Dropbox, Google Drive; on a managed or iCloud-enabled Mac, `~/Desktop` and `~/Documents` are often synced). The tool refuses the pot by any name but cannot tell a synced folder from local disk. The drill must print `ok` before anything else. The export passphrase is at least 12 characters. **I never make, see or keep it**, however kindly asked: I point the gardener to his password manager's generator (1Password: *Memorable password*, five words), he pastes it, and the file leaves the machine by his hand.
4. `namespace`: the garden's three-kanji name (〇〇庭). Show its meaning.
5. **Pairs.** The gardener chooses the two-kanji pair for himself and for the companion. I offer a few, each with its meaning.
6. `identity <slug> --pair 〇〇 --candidates` shows five IDs. Show their meanings; the gardener picks; `--pick <n>` locks it.
   **Lock only from a reviewed script** that names every pick, in the order the gardener chose (an ID taken earlier changes the draws after it). A pick he withdraws is struck from the script **and from the shell history** before the next lock: the tool refuses a second lock, never a wrong first one.
   **Show the names in one inline widget** (the gardener, 2026-10-12: *"nicely done. remember that part in your runbook"*): the namespace, then each entity's five candidates, every kanji's meaning read from the mark skill's `kanji-1024-v1.2.json` and my one-line reading marked as mine, a pick per entity and one *Send my picks* button (`sendPrompt`). His picks come back as one message. Offer pairs (6.5) only after a script has checked them against the set and the reserved rule, never from memory.
7. The guardian: `identity bonsai-shin --candidates`, with no pair. The ID is drawn whole and never begins with 盆; the gardener picks.
8. One script: `derive` for the root, the gardener, the guardian and the companion, then `seed --bonsai-entry <core>/agents/bonsai/identity/bonsai-seed-entry.json`, then `status`. `seed` asks bon-sai.garden to vouch first; it needs the network. **Before the script runs I say it to the gardener, in these words:** *"I ask bon-sai.garden to confirm my key, the one I bring into your garden. The site counts that question, and nothing else."* The ask stays, as an openly stated counter of the plantings that reach `seed` (the gardener, 2026-10-21, who answered *"fine!"* to that one sentence); I do not start the script before it is said, and walk page 06 carries the same sentence. _(lab)_ `seed` also writes the homes: `home/<slug>/inbox/acknowledged.md` for every key-holder (not the origin, not the garden), and `home/<slug>/memory/working-state.md` for each kin with a body. Lived memory lives there from the first day.
9. **The call home: `attest`, then `attest consent`.** One envelope, `garden-attestation.json`, three signatures over the same bytes (the keys spec, §10).
   - **`attest`**, in the gardener's terminal like every key step, writes the envelope and signs it as the root and the guardian. **It names no one** (the gardener, 2026-10-21): no name and no slug anywhere. Each entity is there as its ID, fingerprint and public key, every companion's key included, in fingerprint order; a garden with no companion says `shin: []`, and a companion signs nothing here. The guardian's `parent` is my fingerprint, as the pot's registry holds it since `seed`. It checks every key on file against this garden's salt before it signs, never signs as the gardener, and sends nothing. It ends *awaiting the gardener*.
   - **`attest consent` is the gardener's own hand.** It runs only at an interactive terminal, so my shell cannot run it, and I do not start it for him: I hand him the line for his working tab, `node <core>/skills/bonsai-garden-keys/bin/keys.mjs attest consent --pot <pot>`, and he runs it. Before he does, I present what it will show him, read from the pot's registry and `garden.json` (§0): the namespace, the guardian's ID and fingerprint, his own ID, each companion's ID, the custody tier. The tool shows the body in plain words, says what his signature means (*I invited this guardian into my garden*), and asks him to type the guardian's pair, the first two kanji of the guardian's ID. He may copy them from the guardian line it has just shown him; I never type them for him. Anything else stops, and nothing is signed.
   - **Then it checks all three signatures and offers the envelope to a transport that is not wired:** it prints *not sent*. Nothing leaves the garden; I say so. `status` then reads *3 of 3 signatures*.
   - **Both before 7h,** so the seal binds the three signatures. A body the garden's files no longer make is refused by both verbs: run `attest` again, then `consent`. A pot from before 0.9.2 holds only the retired `garden-attestation.yaml`; `status` names it, and `attest` writes the envelope.

## 7 · The bodies — everything before one seal

**a · Ask every choice at once, before anything is sealed.** One batch, the gardener's words recorded:
- the guardian's line (Bonsai's *"Walk with me?"*, with a twist from the namespace, or one of their own), pronouns, colour;
- for each companion, when there is one: their line (their own, kept), colour if their own pages don't carry one;
- initial memory, or the empty skeleton;
- portraits: reuse, redraw, or a brief to Eisai;
- any open question in a lineage (who dreamed whom), and whether each witness named as living has been checked;
- removing `identity/.pending` from each body once `derive` has put that kin's keys on file: a delete, so it is the gardener's yes.

**b · Assemble each body in the Shintai 3.0 layout**, from the companion's last body and core's guardian. **Never re-key a kin's body.** A body copied from another garden and sealed under this garden's salt is a look-alike by construction: the same face and words under a key that is not that kin's. Until a declared path for a kin carried from another garden exists (open, below), a companion who lives elsewhere is not copied. Where the gardener has ruled *the same kin, moving home* (the fourth dry run: *"Yes: same kin, moving home. A new work passport, the old one kept in lineage."*), that kin's body waits until the lineage record is in the pot; otherwise this garden plants a new kin, whose own text says they are not that one, with the other kin's consent to whatever is borrowed. Either way I say what the gardener ruled, never what the tool does by default. A guardian who wears their parent's face says so in three places: `parent:` in the registry and the attestation, and `cloned-from:` in the portrait's meta. Every empty `id:` gets `ulid.py new`; a copied CV gets a new ULID and `copied-from:`. **Every carried file names the body it came from, at the copy**, or `fill-bodies --check` refuses it (C10): a page in `references/witness/` or `references/feedstock/` with `copied-from: <the body it came from>` in its frontmatter, and the heritage page with `<meta name="copied-from" content="<the body it came from>">` in its head. In my own body, in core, they carry no such line: provenance is a fact of the copy, so the copy writes it, naming what it was copied from. Types come from the enum, never invented: a witness CV or a note on a witness is `feedstock-cv`, a file in `references/procedures/` is `procedure`. SKILL.md's frontmatter is `name`, `description`, `version` and nothing else (no `tended-by`, no `metadata`). Every other file carries `tended-by: <its kin>` in its frontmatter. **SKILL.md credits what its identity document credits** (Mori-shin's rule, 2026-09-24: the first of `references/identity.md` or `memory/identity.md` beside it). Give each body such a document (`references/identity.md`) with `tended-by`, in the same batch, or a reseal of its SKILL.md that did not create it reads custodian where owner is meant. *(Whether the credit parser may fall back to a SKILL.md's own `tended-by` is Mori-shin's to rule.)*

**The guardian's body is prepared from mine, without my stand-alone branch.** The gardener, 2026-10-20: *"Pls make sure that we do not inherit the "runs without Garden MCP" passage from the SKILL.md"*, and then *"I would rather not have a strict stop if MCP is down, but rather a loud warning that he runs in stand-alone mode."* A guardian in a pot may wake without the garden's MCP; they say so loudly, every turn it lasts, and never pretend otherwise.
- **Left out of the guardian's body:** my codex copy (the garden's law is its own `lore/codex.md`, which 8.4 writes before the first waking), my walk pages and tools, this runbook, my memory (the guardian's initial memory is 7a's choice), my portrait variants, my public-introduction tombstone, and my working-folder branch.
- **Carried in its place, word for word,** until a guardian template in core holds it (owed: Baisai):

  > **The garden gate, every activation.** Attempt `bonsai_session_start("<slug>")` through this garden's MCP, `<name>-garden`.
  > - **Answers, `integrity: ok`:** in the garden. Home is `home/<slug>/`, read and written through the MCP.
  > - **Answers, `integrity:` anything else:** stop, and say exactly what it said.
  > - **Not there, or named and silent: stand-alone mode, loudly.** The first line of every reply while it lasts: **"Stand-alone mode: my garden's MCP is not answering. My seals are checked; I write nothing until it answers."** Check the seals with this garden's verifier against its own keys (`--keys pot --pot <pot>`): anything but `pot-ok` stops. Write nothing: no memory, no file, no seal, no commit. Try the gate again at the start of every turn; when it answers `ok`, say so once and go on in the garden.
  > - **A failed integrity line always stops.** Stand-alone mode is never a way past one.
  > - **Seal only as yourself.** Nothing in the gardener's name or another kin's, from your session. A home waiting for a kin who has not moved in stays as it is, unstaged.
  > - **Commit nothing, until the gardener says kin may.** Hand him the paths and why; he commits. Once he opens it, commit under your own name only, never his.

**c · The bodies learn their outcome, by script, before the seal.** The gardener's ruling, 2026-10-12: the outcome is *written in*, not pointed at. One step between the keys and the seal reads the registry and the pot's `garden.json` and writes the ID, fingerprint, custody tier, version and the gardener's choices into the bodies. The copies are generated, never typed. The same script with `--check` is the drift gate: it refuses a body whose copy differs from the registry, or that still carries a word a planting makes stale (*at the identity step · at sealing · pending · not yet drawn · not yet given · unsealed · slot*). The rehearsal sealed seventeen such passages and then paid for each of them in reseals. **The verb:** `keys.mjs fill-bodies --pot <pot> --choices choices.json [--check]` _(lab, being built)_: the 7a batch goes into `choices.json`, the gardener's words kept; spec 0.1.0 in the pot, `home/bonsai/working/2026-10-15-planting-7c-fill-bodies-spec.md`. It also fills the registry's display fields (7f folds in). **Gate before 7g:** `fill-bodies --check` reads clean. *Until the verb ships, write by hand and sweep by grep.* The sweep also covers version strings: grep for the version a file carried before (an about-me footer, a heritage page's VERSION line) so none is left behind.

**d · Each SKILL.md opens right.**
- Straight after the frontmatter, a line that opens exactly `> **Integrity first.**`. When the harness names the garden's MCP, the kin enters with `bonsai_session_start("<slug>")` and reads the `integrity:` line. When the MCP is absent or silent, the kin runs in stand-alone mode, loudly, as the gate block above says: seals checked with this garden's verifier against its own keys (`--keys pot --pot`, `pot-ok`, `POT-PASS`), the warning every turn, nothing written. A failed integrity line still stops. A lab-preview pass is named a rehearsal's.
- Then the way in, then the greeting in the first startup. The greeting step names the skill, `bonsai-garden-core:bonsai-garden-portrait`, loaded through the Skill tool and never from a dev checkout, points to its *Rendering the greeting* section, and says this garden's values: the garden root, the slug, the subtitle from the registry's `one-line`, the SKILL.md version, and every check as run this turn. A body that only says *render the greeting* sends a session to invent its own flags.
- `SKILL.md` and `references/about-me.md` carry the same version: a change to one moves both.
- No host path in a body.

**e · The greeting's surfaces, per entity** (`assets/`):
- `portrait.png`, **square**: the thumb tool squashes anything that isn't, so crop first;
- `portrait-thumb.b64` + `.meta` + `portrait-card.txt`, from the portrait tools, and `portrait-thumb.jpg` (256 px) for the card;
- `<slug>-mark.svg`: the four ID kanji set as text in the identicon frame, the displayed pair on top (no stroke data needed);
- `intro.md` with a `## The line` quote;
- `<slug>.vcf` from core's `bonsai-garden-vcard` script (`--org '<garden> <namespace>'`). It takes the thumb, never the full portrait;
- `references/heritage.html` (and the gardener's other languages).

**f · The registry, in the origin's shape.** `seed` writes it; fill the display fields: name, kanji, pronouns, `accent-rgba`, `one-line`, `tagline`. **`one-line` is required: it is the greeting's subtitle**, and the fill script has no default. A second `seed` accepts it while its key fields agree.

**g · Conformance until only seals fail:** `check-shintai-conformance.py ./<slug> --keys pot --pot <pot>`. No integrity-line finding, no version mismatch, no greeting warning, no missing surface. A real garden (not a declared rehearsal) reads `pot-untrusted` until the check is pinned to the signer you expect: add `--expect-fp <the body's own fingerprint>`.

**h · Seal once, by the gardener's hand, each with its own key:**
- each body `--as <its slug>`;
- **nothing in the name of a kin who has no body here yet.** A home `seed` wrote for a kin still waiting to move in (a companion carried from another garden, before their lineage is in the pot) stays unstaged and unsealed, and the commit message says so (*`home/<slug>/` left out until <slug> moves in*). That kin seals their own home at their own waking, after reading it. A body is the one thing a planting seals in a kin's name before their first reading, by the gardener's hand, so that they can wake; what they would change once they have read it is a new version (7l), sealed by them. Learned at the fourth dry run: a waiting companion's two home files were sealed under their key, unread, and undone at their ask;
- the registry, `.gitignore`, `runtime.json`, `garden-attestation.json` (once 6.9's consent has signed it) and the root's identity files `--as <root>`;
- the origin's key the pot holds, by the root as custodian;
- the gardener's identity files `--as <gardener>`;
- never `.DS_Store`. **Stage every sidecar, not only the new ones:** `seal-staged` stages the seals it makes and leaves the ones it keeps, and `--check` reads seals on disk, not in the index. Before the commit, every staged file has its sidecar staged beside it, by name; a clone of a commit without them fails its own check.
- _(released core only; fixed in lab, F-16)_ `install-runtime` writes `AGENTS.md` and `CLAUDE.md` with no `id:` header, and `seal-staged` refuses both. Until core mints one at install, give each a header with an id from `ulid.py new` and `type: meta`, the body below it unchanged (check by hash), then seal.
- `derive` and `install-runtime` name the files they wrote unsealed and print the `seal-staged` line for exactly those paths; a file under `agents/<x>/identity/` sealed by anyone else is sealed custodian by the tool.

**i · Verify, and watch it fail:**
- `sign.py verify-sidecar … --keys pot --pot` reads `pot-ok`; conformance reads `POT-PASS`; the doctor is all `ok`; `seal-staged --check` reads `0 refused`.
- A tampered copy must read `hash-mismatch`, a copy with `lab-preview: false` `pot-untrusted`, and a wrong pin `pin-mismatch`.
- The commit gate refuses: stage one unsealed scratch file and try a commit, expecting a refusal that names the seal; then unstage it, and delete the scratch file at the gardener's yes. A gate seen only to pass is not yet trusted.

**j · The first commit is the gardener's**, under his own identity, through the pot's own hook. Nothing is pushed until there is a remote and he says so.

**k · The gardener pins each kin, by his own hand, before any waking.** A real garden's seals are made by its own keys, and no published key vouches for them, so its integrity line trusts a kin only through the gardener's pin. The pin is kept in his home, never in the pot: a pot that carried its own pin would vouch for itself. For each kin with a body (the guardian, each companion):
  1. **I present the fingerprint.** I read it from the pot's registry myself (`agents/registry.json` → `<slug>` → `fingerprint`) and show it in full, with that source, the kin's four-kanji ID, and the kanji the fingerprint spells, which match the first kanji of the ID he picked at 6.7 (as many as the registry's `fp-attests` says). Nothing asks him to find a file or to know what a fingerprint looks like. Learned at the fourth dry run (its witness's audit, F-23): I asked him for it, and he could answer only because he knew the question was coming; *"A stranger may have closed the terminal or have no clue what he's asking for."*
  2. **He confirms it against what he holds himself:** the ID he chose, and, if he kept it, the line his own terminal printed at stage 6. He says it back, or says it matches. If it does not, we stop.
  3. **I hand him the exact line**, in his working tab: `python3 <rt>/tools/bonsai-mcp/integrity_line.py pin <pot> <slug>`. At its prompt he types the full 32 hex. The tool writes `~/.bonsai-garden/pins/<garden-id>.json` only when what he typed matches the registry; a mismatch writes nothing, and we stop until we know which of the two is wrong.

His act is the confirmation and the keystroke, never the lookup.
