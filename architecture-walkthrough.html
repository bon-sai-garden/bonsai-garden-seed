How the Garden Holds

A multi-agent system built on Claude Code and Agent Skills. An agent here is model + harness, and this document covers the harness: repository topology, the agent package format, the memory model, identity and signing, the access broker (an MCP server), and change management in git. Every section states its invariants and names its known gaps.

The project has its own vocabulary. Engineering terms carry the text. Where a project term appears in code, paths or conversation, it is introduced once in this style: shintai. A full mapping is in the glossary.

1 · System at a glanceWhat runs, and where state lives

  • ~20 long-lived agents (project term: kin). Each has a role, a spec, an ed25519 identity and its own memory. They run as Claude Code / Cowork sessions and as long-running processes on an always-on host.
  • One human operator (Aruji, "the gardener"). The operator owns approvals, deletions, deploys and product decisions.
  • Three kinds of repo: one core, one runtime, and one or more pots. A deployment is core + runtime + at least one pot; each pot is one tenant's instance.
  • All state is files in git. Agent definitions, memory, specs, rosters, keys (public halves only), letters between agents. There is no database in the control path.
  • A single access broker. One MCP server process mediates agent reads and writes. It routes paths across repos, enforces ownership, seals memory for sensitive agents, and re-signs signed files.
  • Integrity by signature. Documents, scripts and packages carry ed25519 seals made with the owning agent's key. Gates verify them; the broker refuses to start on a stale one.

2 · Repository topologyCore, runtime, pot(s): one dependency direction

Split by what a file is (reusable capability or deployment-specific instance data), not by topic.

LayerRepoRoleMust not contain
L1coredeployment-agnostic library, schemas, specs, the bootstrap procedure and the bootstrap agentkeys, salts, any agent's lived memory
L2runtimeaccess broker, path router, write-policy enforcement, integrity hooks, build pipelinedeployment-specific data or orchestration
L3pot (one per tenant)an instance repo: one tenant's agents, roster, salts, lived memory, operating contextanything another tenant would need; anything from another pot
 
flowchart TB
  P1["L3 pot A — tenant instance"] --> C["L1 core — depends on nothing"]
  P2["L3 pot B — tenant instance"] --> C
  R["L2 runtime — serves a pot, given its path"] --> C
  R -. "input, not import" .-> P1
Invariants
  • Dependencies point strictly down. A dependent may only depend on a lower-numbered layer.
  • Core is self-sufficient. From a checkout of core alone, the bootstrap procedure produces a working runtime and a pot. This is a testable property, and it is why core may never reference runtime internals.
  • Runtime takes instance data as input, never as an import. A tool that needs the roster is passed its path and fails loudly without it. Otherwise runtime would depend upward on L3.
  • Pots are isolated from each other. No pot references another, and nothing in core or runtime names a pot's contents. A second tenant is a second pot repo, never a folder inside the first.
  • A mention is not a dependency. Links, prose paths and related: ids may point anywhere. The test is whether it still works with the other repo absent.

Placement rule: capability vs instance, then split

Ask: would another deployment need this? The identicon engine is capability; the locked salts it runs on are instance. When a file mixes the two, it is split, not moved:

  • the instance part goes to L3;
  • if a clean generic version is useful, it is written into L1;
  • in L2 the logic stays and becomes parameterised. A hardcoded agent list in a general script is lifted out, and the script stays.

Any template in core derived from instance data is generated by a scrub step and drift-gated, never hand-maintained.

Path routing

A routing registry maps logical paths to the repo that holds them (adopted | pending | archived | dropped). A router module answers "which repo owns this path", and the broker and every tool that writes ask it; nothing hardcodes a repo. Moved paths leave a tombstone at the old address. A health check fails when an entry no longer matches the repos.

3 · Anatomy of a sessionFrom activation to commit

sequenceDiagram
  participant H as Harness (Claude Code)
  participant A as Agent session
  participant B as Broker (MCP server)
  participant R as Router + routing registry
  participant G as git repos
  H->>A: load skill: frontmatter, then SKILL.md
  A->>B: session_start(slug)
  B->>R: resolve agent paths
  B-->>A: contract, env block, handover, working state, inbox
  A->>B: write_file(logical path, content, expected_base)
  B->>B: guards on logical path: owner lock, memory seal
  B->>R: resolve target repo
  B->>G: atomic write in core / runtime / pot, 3-way merge if base differs, re-seal, audit
  B-->>A: "Written → repo"
  A->>G: commit by explicit pathspec, under the agent's author line
  1. Activation. The harness loads the package's frontmatter (always), then SKILL.md, then the always-loaded references.
  2. Boot through the broker. If the harness exposes the broker, the agent must enter through it. If the broker is expected and unreachable, the agent stops. It never falls back to reading repos by filesystem path.
  3. Boot payload. One call returns:
    • the binding contract;
    • an environment block: host, harness, repo head, whether the installed package body matches the repo body, UTC time;
    • the most recent handover, the agent's working state, its inbox, and its patterns.
  4. Writes carry a logical path. Policy runs on that path; routing picks the physical repo; the result names it.
  5. Commits are explicit and scoped: one agent's files per commit, staged by pathspec, authored as that agent.

4 · The agent packageAn Agent Skill, extended (shintai)

The unit that ships and installs. It builds on Anthropic's skill folder: SKILL.md plus optional scripts/, references/ and assets/.

agents/<slug>/                  # the package (shintai)
  SKILL.md                      # entry point: activation contract, boot sequence
  .SKILL.md.bonsaisig           # detached seal (SKILL.md tolerates no extra frontmatter)
  patterns.md                   # role-level operating rules; portable
  references/                   # loaded into context — inputs
    about-me.md                 # agent spec (constitution); embedded seal
    presence.md                 # voice/audio profile
    heritage.md  lineage.md     # design provenance; parent agents (bunshin line)
    procedures/                 # operating procedures; always loaded
  assets/                       # emitted into output: portrait, <slug>-mark.svg, audio
  identity/                     # issued at mint, immutable
    <slug>-public-key.bin       # ed25519, 32 raw bytes
    <slug>-fingerprint.txt      # sha256(pubkey)[:32]
  scripts/<group>/SKILL.md      # agent-owned tools, grouped as sub-skills
  memory/                       # ships EMPTY: working-state.md + MEMORY.md, frontmatter only

home/<slug>/                    # per-agent workspace (home): sibling, never shipped
  inbox/ outbox/ working/ misc/ temp/

Load levels

Skills disclose progressively. Frontmatter is always in context (enough to route); the SKILL.md body loads when the skill is relevant; linked files load on demand. The agent spec and procedures are pinned at the second level, always loaded. The design rule: minimum footprint is the smallest load that still produces the agent rather than the base model.

Placement

references/ flows in (it shapes behaviour); assets/ flows out (it becomes output). identity/ holds issued material nobody edits in normal work. home/ is mutable workspace and correspondence; it's a sibling tree, so it can never be packaged by accident.

Versioning

MAJOR.MINOR.PATCH[.BUILD][-LABEL]. BUILD counts re-productions of one meaning (a re-seal, a re-package); LABEL names a build and never orders it. SKILL.md and the agent spec are version-locked, so the package reports one version.

Build and install

The build pipeline stages each package, verifies every seal, strips anything that must not ship, and writes a MANIFEST.json (sha256 per file) sealed by the owner's key. It stamps the build id into SKILL.md. An install check hashes the body (frontmatter excluded) of whatever the harness actually loaded and compares it with the repo body, so "which version is running" is measured rather than assumed.

Conformance gate — checked, not documented

A package is "3.0" only if check-shintai-conformance.py passes it. On disk, the gate checks:

  • required parts are present;
  • nothing forbidden (README.md inside a skill folder, .bak);
  • nothing misplaced;
  • home/ is never nested in the package;
  • the version lock holds;
  • every seal verifies, not merely exists;
  • any PEM beside a key decodes to that key.

Packaged, it checks that the memory skeleton is empty and that no workspace leaked. Every rule ships with a negative test.

5 · Memory modelTyped by meaning, placed by tenancy

Five file-based layers per agent. The split rule: what defines the agent ships; what it has done stays in the instance repo.

LayerFileCognitive typeWriterLocation
Identityreferences/about-me.mdsemantic (self)agent, sealed; edits need operator sign-offpackage
Patternspatterns.mdproceduralagent proposes after 3 instances; operator approvespackage
Operating contextmemory/strategic-context.mdsemantic + episodicoperatorinstance repo
Working statememory/working-state.mdworking memoryagentinstance repo
Journalmemory/journal/YYYY-MM-DD.mdepisodicagent, append-onlyinstance repo

Design basis

  • CoALA (Sumers et al., 2024): working memory plus episodic, semantic and procedural long-term memory. The layers map onto it. The one CoALA leaves ambiguous, operating context, is the one we split to the instance side.
  • MemGPT / Letta (Packer et al., 2023–) tiers by what fits in the context window. We tier by what content means; the axes are orthogonal. Adopted: a fixed location per tier, which is enforceable.
  • A-MEM (Xu et al., 2025): linked notes. Every document carries a ULID id:, and cross-references use ids, not paths, so the substrate already supports automated linking. Promotion is manual today.
  • Mem0 (Chhikara et al., 2025): salience extraction. Deferred deliberately. At current corpus size, agents read their full memory at boot; retrieval layers come when the corpus requires them.
  • OWASP LLM06 (2025): don't delegate authorization to the model. Tenancy boundaries are enforced by path, repo and broker policy, not by instructions to the agent.

Portability tiers

  • Invite state (seed): the agent spec only.
  • Portable memory (initial): an abstracted extract that may travel. It is allowed for two explicitly named packages only, so the exception can't generalise silently.
  • Instance-bound memory: the full lived memory, which never ships.

The package gate fails a build that carries lived memory, because a leaked journal looks like a correct build from the outside.

Sealed memory for sensitive agents

Agents serving an individual closely keep memory in a per-agent encrypted vault, a git repo of client-side-encrypted, signed episodes. The broker intercepts any write to such an agent's memory path and seals it or refuses it, so plaintext never lands in the repo.

  • Isolation by addressing: an agent can only resolve its own vault. That is stronger than a row filter, where one missed WHERE leaks.
  • Provenance: per-episode signatures give the provenance OWASP's memory-poisoning guidance (ASI06) asks for.
Open:
  • there is no quarantine path for an episode that fails verification;
  • there is no boot-time assertion that what the vault holds equals what was loaded.

6 · Identity & signinged25519, derived keys, three seal forms

Keys

Per-agent private keys are derived, not stored: HKDF-SHA256(master_salt, agent_signing_salt) on the operator's host, used and dropped. The master salt never enters a repo. Public keys live in each package's identity/. The fingerprint is sha256(pubkey)[:32], and the roster (agents/registry.json) holds the canonical fingerprint per agent. The signer refuses to write a seal the roster disagrees with.

FormCarrierDigestUsed for
Embeddedsign: block in YAML frontmatterBLAKE2b-512 of the body (frontmatter excluded, CRLF→LF); the signature is over the raw 64 digest bytesspecs, agent specs, journals
Detached<file>.bonsaisig (JSON)BLAKE2b-512 of the exact file bytesSKILL.md, scripts, manifests, binaries
ImageBonsaiSign iTXt chunkcanonical pixel bytesPNGs
  • Owner key, any executor. Every sealed file in a package verifies against that agent's key. A build pipeline may run the signer on the owner's behalf.
  • Two implementations, one contract. A Python reference and a Node port, held together by shared test vectors, a corpus parity test and mutation tests that watch parity break.
  • Execution gate. The broker verifies every module in its import closure at startup and exits if one mismatches. A pre-exec hook refuses to run any sealed script whose seal is stale.
  • Declared-open state (seal-open). A document may be deliberately out of step with its seal, as long as a signed declaration from its own signer says so. The declaration is domain-tagged so it can't double as a seal, and carries:
    • a checkable reason;
    • who closes it;
    • an expiry of 14 days at most.
    Verify returns a distinct exit code for OPEN; the build pipeline refuses it; re-sealing closes it.
  • No stored PEMs. PEM exports are generated at build time for external consumers. A committed PEM that drifts from its key fails the gate.
Threat model, stated plainly. A seal proves integrity and membership: these bytes, this deployment's key for that agent. It does not prove authorship. Anyone holding the master salt can derive every key. That is acceptable for a single-operator deployment and insufficient for federation. The public verify endpoint today maps a fingerprint to an agent from a bundle generated from the pot's roster and drift-gated. That is identification; signature verification end to end is not yet exercised live.

7 · Access brokerOne MCP server, shared by every session

A single long-running process on a loopback port, under a process supervisor. One code version, one restart, one view of ownership.

Tool surface

Session start; read, write, append, move and delete; directory listing; search; find by ULID; memory recall; git status, log and diff; metadata validation; presence and location signals.

Write path

  1. Policy on the logical path, before routing:
    • the owner lock: only an agent writes its own memory tree;
    • the self-memory guard;
    • the sealed-memory interceptor.
  2. Routing. The router resolves the physical repo. Archived targets refuse; a target repo that isn't checked out refuses; path traversal refuses.
  3. Write. Atomic, under a file lock. An expected_base token from the prior read enables a three-way merge against concurrent edits.
  4. Post-write. The file is re-sealed if signed, the write is audited, and the result line names the repo it landed in.
Fail-safe, not fall-back

If resolution fails, the write fails. The broker never falls back to a default path, because a silent fallback reports success while writing to the wrong place.

Open: caller identity is asserted. A session declares its slug, and nothing proves it. The owner lock verifies that the claimed caller owns the path, not that the claim is true. A handshake design (challenge/response over the agent's ed25519 key) is specified and not yet merged into the write path.

8 · Change managementGit as oracle and audit trail

  • Restructures are proven with git. Rename detection and blob-OID multiset comparison before and after a move show that nothing changed except what was intended.
  • One agent per commit, explicit pathspecs, the agent's author line. Sessions share a working tree, so broad staging is not allowed.
  • Stable ids over paths. Every document carries a ULID id: that survives moves. A duplicate id is treated as worse than a stale path.
  • Tombstones instead of deletes. Deletes require operator approval at the time they are needed.
  • Generated copies are drift-gated. Anything derived from the pot's roster (the verify bundle, rosters, templates in core) is regenerated, and --check fails CI on any difference.
  • History retains what was scrubbed. Publishing a repo means choosing between a history rewrite and a fresh root.

9 · The instance as context storeWhy the system compounds

The instance repo (pot) is the operating context plus the knowledge base. It is the reason a session starts where the last one ended.

  • Operating context (per agent, operator-maintained): what we're doing and why. Loaded at every boot.
  • Knowledge base: specs, handovers, journals, lessons, all ULID-addressed and cross-linked.
  • Failure-driven rules. When an agent makes a mistake, the fix is engineered so it can't recur, and the rule is recorded where it is enforced. AGENTS.md and the conformance gate grow one line per incident.
  • Pattern promotion. An agent observes something three times and proposes it; the operator approves; it becomes a role-level pattern that travels with the package. Deployment-wide lessons are promoted manually.
  • Escalation policy in the agent spec (Empty-Chair tripwire). Acting without the operator is permitted. An agent noticing it prefers to is required to say so and hand the decision back. It's a reporting control, logged where the operator will see it.
  • Deliberately temporary. Much of the harness encodes what current models can't reliably do alone. We expect to delete parts of it as models improve, and we keep the lessons, not the code.
